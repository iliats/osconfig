# Top seven confirmed issues in the legacy E2E tests

These issues are ranked by criticality. Each one is directly visible in the current implementation; the descriptions distinguish the definite code defect from runtime effects that occur only when the relevant failure path is exercised.

1. **A timed-out test keeps running in the background:** The shared runner creates a child context with a deadline, but the test callback does not accept that context. Instead, the callback is launched in a goroutine and the runner returns as soon as its separate timeout fires (`e2e_tests/test_runner/test_runner.go:40`, `e2e_tests/test_runner/test_runner.go:59-80`). Nothing cancels or joins the callback. Therefore, after the runner has recorded a timeout, the old attempt can continue creating, modifying, or deleting cloud resources and can even keep writing to the already-finished JUnit test case. This makes later tests and retries vulnerable to interference from work that is officially considered finished.

2. **Patch API retry deadlines use broken duration arithmetic:** Patch polling passes `timeout*time.Second` to `RetryAPICall`, even though `timeout` is already a `time.Duration` (`e2e_tests/test_suites/patch/patch.go:228-239`). Multiplying a duration by `time.Second` scales its integer nanosecond representation by another billion. With the configured 30-minute timeout, the `int64` value overflows to a negative duration, so the retry helper stops after the first retriable API error; with 60 minutes, it overflows to a very large positive duration of roughly 91 years. The helper compares accumulated sleep time with this corrupted value (`retryutil/retry.go:73-105`), so transient API failures are handled very differently from the declared 30- or 60-minute policy.

3. **Resource cleanup failures are not reliably reported or completed:** VM cleanup only prints a deletion error and returns, so the test result can remain successful while its instance leaks (`e2e_tests/compute/instance.go:41-46`). OS policy cleanup uses the test's existing context, derives another timeout from it, and discards the error returned by the delete operation's `Wait` call (`e2e_tests/test_suites/ospolicies/ospolicies.go:303-315`). If the test context has expired, or asynchronous deletion fails, cleanup is not verified. Leaked resources consume quota, retain labels or policy state, and create collisions for subsequent runs without giving those runs a clear explanation of the original cleanup failure.

4. **Individual test/setup errors can terminate the entire test process:** Guest-policy and OS-policy case construction calls `logger.Fatalf` on an invalid setup (`e2e_tests/test_suites/guestpolicies/guest_policies.go:204-210`, `e2e_tests/test_suites/ospolicies/ospolicies.go:228-235`), and guest-policy test-data construction contains a direct `panic` (`e2e_tests/test_suites/guestpolicies/guest_policies_test_data.go:517-522`). There is also a conditional nil-pointer panic in serial-log collection: after `os.Create` fails, execution continues and calls `f.Write` and `f.Close` on the nil file (`e2e_tests/compute/instance.go:172-193`). These paths bypass normal per-test failure reporting; `Fatalf` exits the process, and an unrecovered panic crashes it, so other cases may never finish and their deferred cleanup may not run.

5. **Whole-test retries cannot turn a failed run into a passing run and reuse failed-attempt state:** The shared runner publishes the first failed JUnit case before starting its retry (`e2e_tests/test_runner/test_runner.go:48-55`, `e2e_tests/test_runner/test_runner.go:63-70`). At process exit, `main` fails the run if any published test case has a failure (`e2e_tests/main.go:104-118`). Consequently, a successful retry does not recover the suite: the original failure is still counted. Guest-policy and OS-policy retries also call `runTest` again with the same `testSetup`, including its resource identifiers (`e2e_tests/test_suites/guestpolicies/guest_policies.go:204-229`, `e2e_tests/test_suites/ospolicies/ospolicies.go:228-253`). A retry can therefore encounter resources or asynchronous cleanup left by its first attempt, making it less isolated and obscuring whether it is validating the product or merely surviving stale state.

6. **Core polling and retry loops do not honor test cancellation:** `WaitForGuestAttributes` and `WaitForSerialOutput` have no context parameter and wait only for their own timers (`e2e_tests/compute/instance.go:48-68`, `e2e_tests/compute/instance.go:107-169`). The API retry helper receives a context for calls but sleeps through `currentSleeper.Sleep` rather than selecting on `ctx.Done()` (`retryutil/retry.go:73-105`). An outer test timeout therefore cannot promptly stop these waits. This extends wall-clock time, contributes to the detached-work problem, and delays cleanup while providing only a generic inner timeout rather than the cancellation cause from the test lifecycle.

7. **Capacity exhaustion is returned as a fake zone and cannot be cancelled:** `AcquireZone` does not accept a context. It polls every ten seconds for up to 30 minutes and, on timeout, returns an English error sentence through its `string` return value instead of returning an error (`e2e_tests/test_config/project_config.go:72-103`). Callers then use that sentence as if it were a valid zone, including in machine-type, subnetwork, and disk paths (`e2e_tests/utils/utils.go:521-545`). The resulting failure appears later as a malformed cloud request rather than the real cause—local test capacity was exhausted—and the allocator can keep waiting even after its owning test has been cancelled.
